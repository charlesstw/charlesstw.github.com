openExternalLink無回呼

規格 5.2。問題 4、6。呼叫後 web 完全不知道結果 —— 失敗提示是 App 的責任（5.6）。

人工檢核（5.6）
「找不到 App」情境下，App 端應出現提示告知無法開啟。
「javascript:」「file:」情境下，App 端應靜默忽略、不提示，只記 log。
開完外站後按裝置返回鍵回 App，確認 WebView 仍停在原本頁面、沒卡在 redirect 頁。

downloadFile有回呼

規格 5.3。問題 3。本規格唯一有回呼的方法，最後一個參數是 web 產生的 callbackId。提示由 web 負責，App 端不要另外跳 toast。

首次執行留意相簿權限彈窗。拒絕後再按一次，應收到 PERMISSION_DENIED 而不是無回應 —— 這是 6.4 特別註明的情境：系統不再彈窗時原生仍須回呼。

openEmail無回呼

規格 5.4。問題 5。web 無從得知使用者是否真的寄出，所以呼叫後不顯示任何成功提示。

人工檢核（5.6）
裝置未設定郵件帳號時，App 應提示並顯示客服信箱供複製。
to 留空或格式錯誤時，App 應不提示、只記 log。
有開起來的話，確認中文主旨與換行沒有變亂碼或被吃掉。

回呼監看downloadFile 專用

規格第六章。原生用 evaluateJavascript 呼叫 window._onNativeCallback，靠 callbackId 配回原本那次下載。

目前沒有等待中的下載
範例會自動帶入目前等待中的 callbackId。填不存在的 id 會被記成無主 callback、不做模糊配對，這就是 6.6 的驗證方式。

規格第七章，問題 1、2。與 Bridge 無關，但同一支 App 一起驗。
